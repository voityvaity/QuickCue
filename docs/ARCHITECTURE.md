# Архитектура QuickCue

## Поток речи

`AVAudioEngine → Speech framework (ru_RU, partial results) → debounce 650 мс → QuestionDetector → очередь → LatencyFallbackRouter → AIProvider → карточка/чат → SwiftData`

Детектор вопроса локальный и детерминированный. Он не делает отдельный сетевой запрос. В MVP используются вопросительные слова, вопросительный знак, характерные фразы и команды вроде «объясни», «напиши», «реши». Это намеренно простой слой: после накопления реальных примеров его можно заменить Core ML-классификатором, не меняя остальную цепочку.

## Поток фотографии

`AVCapturePhotoOutput → JPEG → Vision OCR → PhotoStore → AIProvider → AnswerRecord`

Оригинальный JPEG хранится с файловой защитой в `Application Support/Photos`, а SwiftData содержит только относительный путь и метаданные. Для OpenAI и Claude подготовлен прямой image input. DeepSeek/xAI/YandexGPT в текущей конфигурации получают OCR-текст; их конкретная vision-модель может быть подключена отдельным адаптером.

Есть два намеренно разных UX-потока:

- `QuickCaptureController` — один тап на «Эфире» или в «Диалоге», автоматический снимок, OCR и отправка.
- Отдельная вкладка камеры — снимок, предпросмотр, редактирование OCR, пересъёмка или подтверждённая отправка.

## Диалог и роли

`ConversationMessageRecord` хранит реплики владельца, собеседника и QuickCue, состояние ответа и ссылку на локальную фотографию. `SpeakerAttributing` отделяет UI/сессию от будущего механизма определения говорящего.

Текущий `SemanticSpeakerAttributor` не является голосовой биометрией: вопросительные фразы считаются репликами собеседника, остальные — владельца. Роль исправляется явной круглой стрелкой рядом с пузырём; перенос одновременно меняет автора и сторону чата. Настоящая диаризация должна быть отдельным адаптером с явно описанной обработкой аудио и политикой конфиденциальности.

## Провайдеры

Все клиенты реализуют один `AIProvider` и возвращают `AsyncThrowingStream<AIStreamEvent, Error>`. UI не знает JSON-формат конкретного сервиса.

- OpenAI: Responses API, SSE, `store: false`.
- DeepSeek: OpenAI-compatible Chat Completions, SSE, thinking выключен ради latency.
- Anthropic: Messages API, SSE `content_block_delta`.
- xAI: OpenAI-compatible Chat Completions, SSE.
- YandexGPT: OpenAI-compatible AI Studio endpoint и model URI с Folder ID.
- Mock: локальные задержанные фрагменты, нулевая цена, без сети.

Названия моделей находятся в настройках, а не зашиты в бизнес-логику. Это важно, потому что доступные ID и тарифы меняются.

## Latency fallback

Основной запрос стартует сразу. Резервный стартует через настраиваемые 0,8–3,0 секунды. Первый провайдер, приславший текстовый фрагмент, становится победителем; фрагменты второго игнорируются. Завершение экрана не ждёт проигравшего. На следующем этапе стоит добавить явную отмену проигравшего HTTP-запроса на серверной стороне и статистический автоподбор.

## Локальные данные

- `SessionRecord`: границы сессии, счётчики и оценка затрат.
- `TranscriptRecord`: финализированные фразы и признак вопроса.
- `AnswerRecord`: вопрос, потоковый ответ, модель, TTFT, полное время, токены.
- `ConversationMessageRecord`: роль, текст/фото, состояние очереди или ответа, связь с `AnswerRecord`.
- `PhotoRecord`: локальный путь, OCR и связь с ответом.
- `UsageRecord`: токены, тип запроса и оценочная стоимость.
- `SessionStore`: только контекст текущей сессии и координация UI/сервисов.

`SessionStore` держит максимум два активных AI-запроса. Остальные вопросы сохраняются в FIFO-очереди и получают видимое состояние «В очереди» вместо молчаливой потери.

Аудиобуферы не записываются в файл. История не синхронизируется в облако.

## Ограничения MVP

- Только foreground: фоновые audio modes и фоновые уведомления не добавлены.
- Apple Speech может использовать сеть в зависимости от доступности локального recognizer; `requiresOnDeviceRecognition` намеренно не форсируется.
- iOS 26 `SpeechAnalyzer` перспективен для более качественной длинной и удалённой речи, но сам по себе не заявляется как идентификатор личности говорящего. Переход с `SFSpeechRecognizer` выполняется отдельным измеряемым этапом.
- Обычный selfie remote, эмулирующий кнопки громкости, не имеет надёжного публичного callback API. Добавлен честный интерфейс `CaptureTriggering` и BLE-реализация для кнопки с известными UUID.
- Прямое хранение provider API keys в Keychain приемлемо для личного прототипа, но не для массового распространения. Для внешних тестировщиков нужен серверный прокси.
- Денежная стоимость является оценкой по введённым пользователем тарифам; billing API провайдеров пока не сверяется.
