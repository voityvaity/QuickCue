# Архитектура QuickCue

## Состояние 0.3.1

Этот документ описывает реализованный код ветки 0.3.1 с этапами 01–06, а не обещание готовности следующих пунктов дорожной карты. Локальная статическая проверка на Windows не подтверждает компиляцию Xcode, прохождение SwiftData-миграции или работу камеры/микрофона на физическом iPhone. Фактический SHA установленной сборки и результаты устройства нужно сверять отдельно; см. `RELEASE-0.3.1.md`.

## Поток речи

`AVAudioEngine → SFSpeechRecognizer (ru_RU) → TranscriptAssembler → final segment → QuestionDetector → RequestScheduler → LatencyFallbackRouter → AIProvider → карточка/чат → SwiftData`

Partial-текст служит только для отображения: он не отправляется AI. `TranscriptAssembler` подтверждает фразу один раз после `isFinal`. При остановке, смене вкладки или уходе в фон незавершённая гипотеза отбрасывается, а не превращается в вопрос. Вместо фиксированных 650 мс применяется текстовая эвристика ожидания: 500 мс после конечной пунктуации, 900 мс для обычной гипотезы, 1300 мс для короткой/незавершённой. По таймеру приложение просит Speech завершить сегмент, но всё равно ждёт настоящий final; таймаут final — 3 секунды. Это пока не акустический VAD и не доказанная задержка ответа.

Микрофон имеет состояния `idle → starting → listening → stopping`. Поколение запуска делает устаревшие результаты разрешений и callback недействительными. Audio interruption и потеря входного устройства останавливают захват с понятной ошибкой; автоматическое восстановление после явного Stop не допускается.

Детектор вопроса локальный и детерминированный. Он не делает отдельный сетевой запрос. В MVP используются вопросительные слова, вопросительный знак, характерные фразы и команды вроде «объясни», «напиши», «реши». Это намеренно простой слой: после накопления реальных примеров его можно заменить Core ML-классификатором, не меняя остальную цепочку.

## Поток фотографии

`AVCapturePhotoOutput → оригинальный JPEG → Vision OCR → PhotoStore → уменьшенная API-копия → RequestScheduler → AIProvider → AnswerRecord`

Оригинальный JPEG хранится с файловой защитой в `Application Support/Photos`, а SwiftData содержит относительный путь и метаданные. Для сети готовится отдельная JPEG-копия: длинная сторона не более 1600 пикселей, размер не более 1,5 МБ. Для встроенных OpenAI и Claude реализован image input; фактическая поддержка зависит также от выбранной модели и должна проверяться. DeepSeek/xAI/YandexGPT получают OCR-текст. Пользовательская модель отправляет изображение только после явной отметки vision; Chat Completions, Responses и Anthropic Messages формируют разные image payload.

`PhotoTransferDisclosure` до отправки показывает, кому уйдут изображение и текст либо только OCR. Основной провайдер определяет payload: если он получает изображение, резерв без vision отключается, а не подменяет запрос незаметно. В Mock ничего не отправляется. Если пользователь выбрал несовместимый ID модели у клиента, заявляющего vision, интерфейс не может заранее гарантировать её возможности — запрос должен завершиться диагностируемой ошибкой.

Есть два намеренно разных UX-потока:

- `QuickCaptureController` — один тап на «Эфире» или в «Диалоге», автоматический снимок, OCR и отправка.
- Отдельная вкладка камеры — снимок, предпросмотр, редактирование OCR, пересъёмка или подтверждённая отправка; затем результат остаётся на экране с действиями «Открыть ответ», «Копировать», «Переснять».

Оба потока привязаны к исходной сессии и отменяются при смене/завершении сессии и уходе в фон. Снимок, уже сохранённый до отмены, остаётся в локальной истории; отмена не означает его удаление.

## Диалог и роли

`ConversationMessageRecord` хранит реплики владельца, собеседника и QuickCue, состояние ответа и ссылку на локальную фотографию. `SpeakerAttributing` отделяет UI/сессию от будущего механизма определения говорящего.

Текущий `SemanticSpeakerAttributor` не является голосовой биометрией: вопросительные фразы считаются репликами собеседника, остальные — владельца. Роль исправляется круглой стрелкой рядом с пузырём; перенос меняет автора, сторону чата и контекст для следующих запросов AI. Исправленную реплику собеседника можно явно отправить кнопкой «Спросить AI»; уже отправленный запрос нельзя задним числом изменить у провайдера.

Настоящая диаризация не включена в 0.3.1. Для будущего этапа 0.6 выбран гибрид: Apple Speech немедленно показывает текст, отдельный адаптер уточняет роли по коротким перекрывающимся аудиосегментам. Передача аудио потребует отдельного согласия, а биометрический voiceprint не входит в первый вариант.

## Провайдеры

Все клиенты реализуют один `AIProvider` и возвращают `AsyncThrowingStream<AIStreamEvent, Error>`. UI не знает JSON-формат конкретного сервиса.

- OpenAI: Responses API, SSE, `store: false`.
- DeepSeek: OpenAI-compatible Chat Completions, SSE, thinking выключен ради latency. Отдельный `ProviderMetadataClient` читает официальный `/models` только в явном мастере подключения, с ограничением ответа, TTL-кешем без секретов и allowlist рекомендуемых text-моделей.
- Anthropic: Messages API, SSE `content_block_delta`.
- xAI: OpenAI-compatible Chat Completions, SSE.
- YandexGPT: OpenAI-compatible AI Studio endpoint и model URI с Folder ID.
- Custom: любое количество профилей с собственными HTTPS URL, несколькими явно выбранными моделями и протоколом OpenAI Chat Completions, OpenAI Responses либо Anthropic Messages. Основной Bearer/Api-Key/x-api-key и дополнительные секретные заголовки читаются из привязанных к профилю Keychain accounts. Служебные заголовки, credentials в URL/query и cross-origin redirect запрещены. Произвольный четвёртый API-формат без отдельного адаптера не поддерживается.
- Mock: локальные задержанные фрагменты, нулевая цена, без сети.

`ProviderSelection` отличает встроенный сервис от `custom:<UUID>`, поэтому два пользовательских шлюза могут одновременно участвовать в latency fallback и не смешивают ключи. `ProviderProfile` хранит `models[]` и `selectedModelID`; `ModelSelectionPolicy` отдельно фиксирует рекомендуемый и ручной выбор, поэтому каталог не заменяет explicit model ID. Список `/models` подтверждает только обнаруженный ID; text/vision/streaming имеют отдельное значение и provenance, а неизвестность не превращается в `false`. Legacy-профиль преобразуется в один `ModelProfile`, сохраняя UUID провайдера и прежний основной Keychain account. Повреждённый элемент не удаляет корректных соседей, а исходные bytes сохраняются для восстановления.

Безопасный срез B1 добавляет `ProviderSetupCoordinator` для встроенных сервисов. Ручной ввод и локальный OCR сохраняют новый ключ во временный Keychain account; тест использует неизменяемый snapshot и не зависит от Mock. Только непустой полностью завершённый ответ создаёт verified report, копирует кандидат в рабочий account, выбирает сервис основным и выключает Mock. До этого рабочий ключ и routing не меняются. Recovery marker без секрета позволяет идемпотентно закончить уже проверенную активацию после прерывания между Keychain и UserDefaults.

Статус подключения разделён на «не настроен», «не проверен», «проверен», «ошибка». Наличие ключа само по себе не даёт зелёной проверки. Тест соединения ждёт непустой текст и корректное завершение потока; смена настроек во время теста не должна подтверждать новую конфигурацию. В результате сохранены модель, время проверки, TTFT и полная задержка. Тест реального провайдера является реальным сетевым запросом, потенциально платным; Mock не проверяет доступ к аккаунту.

## Ввод секретов

Каждый провайдер использует отдельный основной Keychain account. Дополнительный секретный заголовок получает производный account, связанный с UUID провайдера и UUID ссылки; подмена account при чтении профиля отклоняется. `KeyEditorView` принимает ручной ввод, камеру или системный `PhotosPicker`. `TextRecognizer.recognizeSecret` запускает локальный Vision OCR без языковой коррекции, а `SecretCandidateExtractor` выбирает вероятную длинную строку. Ключ маскируется; временное раскрытие и счётчик символов помогают проверить результат. Приложение не сохраняет снимок ключа в свою историю и не отправляет его AI. Если пользователь выбрал фото из медиатеки, исходник остаётся в медиатеке и её резервных копиях — QuickCue его не удаляет.

## Latency fallback

Основной запрос стартует после выхода из очереди. Для новой установки резерв выключен до явного согласия с возможной двойной оплатой; прежнее сохранённое поведение обновления не меняется. После включения резерв стартует через настраиваемые 0,8–3,0 секунды либо сразу после явной ошибки/пустого ответа основного. Одинаковый `ProviderSelection` не запускается дважды. Побеждает первый непустой текстовый фрагмент, а не пробелы или usage; проигравшая локальная задача и связанный HTTP-поток отменяются.

Отмена на iPhone не гарантирует, что сервис перестал считать токены или выставлять счёт. `AIRequestAttempt` фиксирует каждую начатую попытку, включая проигравшую. Нормальное завершение router дожидается callbacks учёта; UI при пользовательской отмене освобождается сразу, а поздний учёт принадлежит исходной сессии. Если пользователь уже удалил её историю, callback не воссоздаёт удалённые записи.

Поток признаётся успешным только после текста, протокольного признака `.completed` и окончания транспорта без ошибки. Если победитель оборвался, частичный ответ остаётся видимым и не смешивается с другим ответом. Повтор выполняется явным действием; отдельный сценарий «Продолжить резервным» и статистический автоподбор остаются дальнейшей работой.

## Локальные данные

- `SessionRecord`: границы сессии, счётчики и оценка затрат.
- `TranscriptRecord`: финализированные фразы и признак вопроса.
- `AnswerRecord`: вопрос, потоковый ответ, модель/профиль, состояние, ошибка, TTFT, полное время, токены и снимок/версия промпта.
- `ConversationMessageRecord`: роль, текст/фото, состояние очереди или ответа, связь с `AnswerRecord`.
- `PhotoRecord`: локальный путь, OCR и связь с ответом.
- `UsageRecord`: optional session ID, request/attempt ID, владелец/тип работы, точный профиль, модель, результат попытки, безопасный код ошибки, длительность, токены, независимые provenance токенов и денег, снимок тарифа/валюты/даты.
- `SessionStore`: только контекст текущей сессии и координация UI/сервисов.

`RequestScheduler` обслуживает речь, ручные вопросы, фото, вариации ответа и генеративные тесты подключения одной FIFO-очередью. Владелец работы — `session(UUID)` либо `setup(UUID)`: завершение сессии не отменяет чужой setup, а inactive отменяет обе категории. Максимум — два активных логических запроса; каждый может временно запустить primary и fallback, поэтому это не ограничение двух HTTP-попыток на весь процесс. End/Cancel/background отменяют соответствующую работу и очередь; `sessionID` и проверки поколения не дают позднему ответу попасть в новую сессию. Metadata discovery не является генеративной попыткой и не записывается как AI-ответ.

Источник количества токенов различается как полученный от API, грубая локальная оценка или неизвестный. Денежный provenance хранится отдельно: API-reported, calculated или unknown. Непросчитанные отменённые/ошибочные попытки не объявляются бесплатными. Mock явно бесплатен; ошибки отсутствующего ключа/настроек до HTTP помечены `not_sent`. Итог — известная оценочная сумма с отдельным числом попыток без цены. Тест подключения записывается как `connection_test` с `sessionID = nil`, поэтому учитывается в расходах, но не создаёт разговор в истории.

`QuickCueSchemaV1` и `QuickCueSchemaV2` заморожены. `QuickCueSchemaV3` добавляет optional session ID и расширенный учёт попытки; план миграции выполняет V1 → V2 → V3 и V2 → V3. `PersistenceController` открывает прежнее расположение базы, отмечает прерванные запросы отменёнными и завершает незакрытые сессии. При ошибке он показывает экран восстановления и повторное открытие, не удаляет и не заменяет базу. Тестовый модуль `QuickCueLegacyFixture` создаёт настоящую исходную неверсионированную базу; XCTest проверяет миграцию по тому же URL и повторное открытие. Исполнение требует Xcode/iOS.

Аудиобуферы не записываются в файл. QuickCue не синхронизирует историю отдельным облачным сервисом, но системная резервная копия iPhone — другой механизм. Системные логи приложения содержат ID, провайдера, задержки и разрешённые коды ошибок, без ключей, реплик и тел ошибок шлюза.

## Ограничения MVP

- Только foreground: фоновые audio modes и фоновые уведомления не добавлены.
- Apple Speech может использовать сеть в зависимости от доступности локального recognizer; `requiresOnDeviceRecognition` намеренно не форсируется.
- iOS 26 `SpeechAnalyzer` перспективен для более качественной длинной и удалённой речи, но сам по себе не заявляется как идентификатор личности говорящего. Переход с `SFSpeechRecognizer` выполняется отдельным измеряемым этапом.
- Публичные `AVCaptureEventInteraction`/`onCameraCaptureEvent` существуют для активной камеры. Их подключение и проверка конкретного volume/selfie remote относятся к этапу 0.5, не заявлены готовыми в 0.3.1. `CaptureTriggering` и BLE-слой остаются заготовкой для совместимого устройства с известными UUID.
- Общий коммерческий ключ нельзя встраивать в публичный IPA. Возможны BYOK (пользователь вводит собственный ключ в Keychain) либо backend с секретом на сервере; выбор сам по себе не гарантирует прохождение App Review.
- Денежная стоимость является оценкой по введённым пользователем тарифам; billing API провайдеров пока не сверяется.
- Этапы B1/B2/B3a/B4/B5/B6 и B3b-data/protocols реализованы в текущей codex-ветке, но изменения 04–06 требуют нового CI и device update test. Необязательное чтение billing balance DeepSeek не включено: локальный итог не выдаётся за счёт провайдера. Следующими остаются этап 07 и далее из USER-GUIDE; SpeechAnalyzer A/B, продвинутая камера, аппаратные действия и гибрид диаризации не заявлены готовыми.
